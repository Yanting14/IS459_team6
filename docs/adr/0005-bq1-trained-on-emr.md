# BQ1 is a Spark ML model trained on EMR over the bank-visible seven-day features; the frozen GIN is BQ2-only

BQ1 asks whether a model beats banks' rule-based monitoring at ranking accounts for review. The frozen GIN (ADR-0004) cannot be retrained by the team, its training code and split dates are not in the repository, and its daily scores need a separate single-node graph adapter. BQ1 therefore trains logistic regression and gradient-boosted trees with Spark ML on the seven-day account-day features that Prepare already writes to curated, on the same EMR Serverless application, as a re-runnable pipeline step (`train/bq1.py`, `TrainBQ1` in Step Functions). Each run writes a new model version named by its execution; scoring always uses one pinned version, and there is no drift-triggered retraining. A rules baseline on the same features, with thresholds taken from training-day percentiles only, stands in for current monitoring. The model is chosen by mean daily Precision@1,000 on the validation days, a rule written into `metrics.json` before any test day is scored.

BQ1 is strictly one bank's point of view, so the model uses only features a single bank can compute from its own accounts' transfers (`MODEL_FEATURES` in `train/bq1.py`). Prepare's `cp_max_fan_in` and `cp_max_fan_out` are excluded: they count the counterparties' other transfers, and those sit at other banks. Prepare still writes them, and they stay available to other work. The first models (8 November) included them; they were retrained without them, and [BQ1 results](../bq1-results.md) keeps the earlier numbers as a short note.

The GIN is not part of BQ1 at all, not even as a reference column. It sees the shared transfer graph across banks, so it belongs to BQ2 (bank view vs shared view), where its graph inputs make the visibility question meaningful.

Test results are reported on 15 and 16 September 2022 only. Days 1-6 are excluded because their seven-day windows are incomplete; 7-12 September train, 13-14 September validate. The seven-day windows on 15-16 September include transfers from training days. This is not leakage: features carry no account identity, labels are per account-day, and no test-day label or test-day row is used to fit, tune or threshold anything.

Each queued account gets three reasons: the bank-visible features where its value is most extreme against that day's eligible accounts, in a fixed direction per feature (high, low for `hrs_in_to_out`, never for `history_days` and `active_days`). They describe the account; they are not attributions of the model's score, and `ranking.json` says so. The score is a ranking value, not a probability, because negatives are sampled in training.

Labels sit under the same curated prefix as features, so a note cannot keep scoring away from them. Two execution roles enforce it: `bq1-train` reads features and labels and writes `models/bq1*` and `gold/bq1/baseline*`; `bq1-score` reads features and `models/bq1/*` and writes `gold/bq1/queue*`, and names no label prefix. Results are in [BQ1 results](../bq1-results.md).
